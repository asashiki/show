为什么音乐组件会“工具成功，界面失败”

聊天中的播放器不是普通网页。它同时受 MCP 元数据、iframe 沙箱、CSP、媒体 Range 请求和宿主 bridge 约束。

标准优先

新组件先声明 _meta.ui.resourceUri，通过 MCP Apps ui/* JSON-RPC bridge 收取输入和结果；OpenAI 兼容字段只保留为别名。

能力检测

不判断“这是 ChatGPT 还是别家”，而是检测宿主是否提供对应能力。没有组件渲染的客户端仍能读懂文本与结构化结果。

媒体链路

音频由同源代理提供，保留 206、Content-Range 与 Accept-Ranges，并补齐 CSP / CORP / CORS，避免播放器能开却不能播或拖动。

设计依据OpenAI 当前文档明确建议先实现开放 MCP Apps 标准，再用 window.openai 做标准之外的渐进增强。官方说明 →

怎么测试，哪里能“白嫖”

短期测试与长期运行不是同一道题。下面按当前代码是否需要重写、是否保留 SQLite/stdio 能力来判断。

方案适合做什么结论关键限制
现有 VPS 蓝绿最终上线、长期运行、stdio 上游首选新实例换端口/数据库副本；跑完 canary 再切反代，不覆盖老版
本地 Docker + Quick Tunnel从 ChatGPT / Claude 做 1–2 天远程冒烟免费测试电脑必须在线；随机域名；无 SLA；Quick Tunnel 不支持 SSE，因此只验当前请求/响应主路径

这篇文章可以怎么讲

重点不是“追上一个版本号”，而是解释 MCP 聚合器为什么必须从工具转发器变成协议与信任边界。

  1. 从一个 URL 接所有工具说起：为什么 mcp-switch 的产品方向仍然成立。
  2. 协议升级暴露的旧债：重复连接、Schema 压扁、组件 URI 冲突、OAuth audience。

  4. 这次真正做了什么：四个 PR、49 个测试、三种凭据域与蓝绿部署。
  5. MCP 热度退潮之后：少谈“生态万物皆 MCP”，多谈可靠性、可移植 UI 与可审计边界。
